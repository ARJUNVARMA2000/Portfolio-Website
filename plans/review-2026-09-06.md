# Website improvement review — 2026-09-06

Reviewed against commit `eee57e2`. The application working tree was clean at the start. This document preserves the original assessment. The owner subsequently approved implementation; see [the implementation checklist and verification](../tasks/todo.md) for the resulting local changes. The findings and limitations below describe the original review, not the updated website.

## Recommendation

Redesign the homepage around a compact visual overview of the work, then let visitors choose the technical depth. Keep the large name, plain DS/MLE positioning, warm editorial palette, and prominent project destinations. Give finished products, individual contributions, and verifiable results more space than architecture descriptions and repeated labels.

The working assumption is that the portfolio should help recruiters and technical interviewers evaluate Arjun for Data Science and Machine Learning Engineering roles. Its stated availability is January 2027. Conversion impact below is a design judgment, not a measured analytics finding.

### F1 — Evidence wording

Airbnb's “100% numbers cited to source rows” has provenance describing a narrator contract, not a measured evaluation population. ClaimReady lists four specialists, six corpus documents, and four packet documents. These are valid descriptions of the system, but they are visually treated like DEUCE's measured Brier scores. Preserve the role-relevant agent projects and distinguish design guarantees, system scope, and observed results using short visible wording. Do not invent accuracy or success-rate figures.

### F2 — Chat recovery

The API allows at most 20 messages, 2,000 characters per message, and 8,000 total characters. The client submits the accumulated history and has no reset or bounded-context submission. Once a conversation exceeds a limit, later questions continue to fail; the UI calls every error temporary unavailability. Even one long assistant response can make the next request invalid.

The read-only technical audit executed the actual route in memory with a mocked provider: a normal request returned 200; 21 short messages returned 400; a 2,280-character assistant message followed by a question returned 400; and an 8,320-character transcript returned 400. No live model calls were made. Preserve the visible transcript while bounding submitted context, add a new-conversation action, and distinguish length errors, throttling, and provider failures.

### F3 — Chat grounding

Current assistant context includes case-study summaries, metrics, technologies, and links, but excludes `role` and narrative sections. The UI asks “What did Arjun personally build?” and “Which design choice mattered most?” The omitted DEUCE evidence section also explains that the closing market line remains stronger on the matched subset. Supply the relevant existing text with section links; curated context is sufficient at this content scale. Generated-answer accuracy was not tested in this audit.

### F4 — Evidence links

The metric type stores provenance as a single string. Case-study footnote markers are explanatory notes, not external citations, and the homepage only exposes the qualifier through `title`. Extend the record with optional source artifacts, evaluation window, baseline, and a visible qualifier. Use “View evaluation” when a public report exists and a clear methodology note when evidence is proprietary. Avoid presenting unlike evaluation populations as direct comparisons.

### F5 — Supported foundation

The project pins Next 14.2.35 and both workflows use Node 20. Official sources classify [Next 14 as unsupported](https://nextjs.org/support-policy) and [Node 20 as EOL](https://nodejs.org/en/about/previous-releases), checked on 2026-09-06. Use a supported patched Next release and supported Node LTS; verify the deployment's runtime separately because its setting was not inspected. A migration must cover current lint commands, route/metadata APIs, streaming, and navigation regressions.

The production dependency audit reported four high-severity package groups. This review did not establish that their specific exploit conditions are reachable in the site. The counts are not evidence of four exploitable website defects.

### F6 — Historical plans

The old index marks the Next patch, typecheck/CI, and README rewrite TODO even though their main changes exist. Do not rerun those plans blindly or mark every acceptance criterion complete from appearance alone. Reconcile each plan against its actual completion criteria. Prior rejection of a test suite is historical: the site now has a substantive browser suite and more interactions.

## Design and product directions

These are choices, separate from confirmed defects. The recommended order is D1, D2, then a prototype of D3; D4 is useful if discovery remains awkward after D1.

### D1 — A compact visual homepage

**Value:** A visitor should quickly see the range and quality of the work, identify relevant experience, and choose one project. The current forced project height and long introduction obscure that overview. Evidence: `app/page.tsx:29`, `components/home/evidence-workbench.tsx:81`, `components/home/hero.tsx:134`, and live measurements above.

Proposed order:

1. Name, concise factual role/credentials, availability, a clear Selected Work action, and direct Resume/Contact links.
2. A compact selected-project gallery using actual product screens or outputs. Each entry states what it does, Arjun's contribution where verified, one meaningful piece of evidence, and its available Live/GitHub/Case Study actions.
3. A concise Novo Nordisk / ZS / Columbia experience summary, with fuller role history available below or by expansion.
4. One featured technical walkthrough, opened by deliberate choice.
5. The remaining project directory, a brief personal/about section, and contact.

Keep the name large and the copy factual. On mobile, reduce the portrait's prominence and bring the first project into view sooner. Increase small text where readers need it to understand the project: the current metrics and technology labels frequently use 9px text (`components/home/evidence-workbench.tsx:97`, `:102`). Use larger product imagery, less repetitive framing, and motion for transitions and evidence relationships. Replace the moving wall of skill chips with a few capabilities linked to work that demonstrates them (`components/home/about.tsx:62`, `:97`).

**Effort:** M–L. **Risk:** Medium; preserve working anchors, project destinations, static content, keyboard operation, and reduced-motion behavior. **Confidence:** High on the layout evidence, medium on conversion impact. Start with desktop/mobile prototypes and a short task-based review, not a framework rewrite.

### D2 — Make personal contribution and engineering judgment easy to find

**Value:** Technical interviewers should be able to see what Arjun built, what decision mattered, what was measured, and what remains limited. The case-study model has a role field but the homepage does not render it; ClaimReady's featured record describes the collaborative product without an individual contribution field. Evidence: `content/case-studies.ts:28`, `:45`, `:151`; `components/home/evidence-workbench.tsx:10`; `components/home/work-list.tsx:24`.

Give each featured project a short “My contribution / Key decision / Result / Limitation” summary before the deeper narrative. Reuse verified material such as DEUCE's chronological evaluation and honest market comparison. Establish ClaimReady contribution details with the owner before writing them. Pair this work with F1 and F4 so each result has appropriate context and accessible evidence.

**Effort:** M, plus owner input for missing facts. **Risk:** Low if new claims are verified. **Confidence:** High on the missing presentation, medium on hiring impact. The trade-off is a modest editorial effort that must stay consistent with the resume and project repositories.

### D3 — Extend the strongest interaction into a real inspectable example

**Value:** The existing Airbnb replay already shows a recorded failure and recovery. DEUCE and ClaimReady currently switch explanatory text and field labels; those panels could show actual inputs and outputs. Evidence: `components/home/work-list.tsx:14`; `components/home/workbench/deuce-signal-inspector.tsx:5`, `:92`; `components/home/workbench/claimready-handoff-inspector.tsx:5`, `:43`.

Prototype one of these:

- A recorded DEUCE match dossier: information available before the match, frozen forecast, model/market comparison, and eventual result. Use sourced artifacts; do not invent probabilities or imply that a text-selector runs the production model.
- A ClaimReady example showing a sample input, the fields each stage added, a validation problem, and the resulting document excerpt. Label synthetic examples as synthetic and recorded examples as recorded.
- A stronger presentation of the existing Airbnb trace: lead with the question and final cited answer, then let readers inspect the failure, validation, and recovery that produced it.

**Effort:** L, coarse estimate; constrain the first spike to one project. **Risk:** Medium, chiefly artifact accuracy and maintenance. **Confidence:** High on the capability gap, medium on strategic value. This is the most distinctive direction, but it needs credible example material before UI construction.

### D4 — One coherent project directory

**Value:** The current search only sees five secondary projects. It cannot find DEUCE, Airbnb, BTC, or featured ClaimReady. “Work” and “Projects” therefore lead to different rosters. Evidence: `components/home/project-index.tsx:7`; `components/home/project-explorer.tsx:12`, `:37`; `components/home/work-list.tsx:7`.

Use one registry with featured status, capability tags, verified ownership, and optional destinations. All relevant projects become discoverable while editorial prominence remains intentional. If the homepage keeps a scoped secondary search, label the scope clearly instead. Capability filters could then connect forecasting, agent engineering, retrieval, and production ML across the complete portfolio.

**Effort:** M. **Risk:** Medium because content feeds the homepage, case studies, chat, and metadata. **Confidence:** High on current scope, medium on the value of richer filtering for a small portfolio. Avoid adding elaborate search infrastructure.

## Sequence and verification

Recommended selection: **D1 + D2, with F1–F4 in the same release stream**. Complete a compact visual prototype before changing the homepage architecture. Source verification precedes new ownership/results copy; evidence artifacts precede D3. The supported-runtime migration can proceed separately with its own regression gate.

Current commands: `npm run typecheck`, `npm run lint`, `npm run build`, `npm run test:e2e`; `npm run check` composes these. Browser tests support `PLAYWRIGHT_BASE_URL` for a dedicated known server. Avoid inadvertently testing an unrelated application already on port 3000.

For selected plans, extend existing focused tests rather than mirror implementation details: conversation boundary/recovery tests against the actual route; context fixtures covering ownership and limitations; all-project search only if its scope changes; desktop/mobile navigation and project-link checks. Compare the revised homepage's reading path and length at the observed desktop and mobile sizes. Validate keyboard use, reduced motion, no-JavaScript content, and actual destinations before completion.

## What was preserved or rejected

- Do not propose a hero stat strip or slogan. Existing owner preferences explicitly reject them.
- Keep generic DS/MLE positioning; healthcare experience belongs in relevant work rather than becoming the entire identity.
- Do not demote role-relevant agent projects just because forecasting currently has stronger quantitative evidence.
- Do not recommend adding trace replay, contextual chat prompts, structured metadata, project actions, or browser tests as if absent. They exist.
- The archive treatment of SunCulture and absence of an invented ClaimReady case study are deliberate, not bugs.
- Motion is an intentional design choice. No generic animation-removal or bundle-size finding is justified without a measured cost.
- A new CMS, framework replacement, or large retrieval service is not justified by this audit.

## Scope and limitations

Reviewed the rendered homepage at desktop and mobile sizes, a representative DEUCE case study, the shared article layout, content models, project discovery, chat boundary/context, motion lifecycle hotspots, dependencies, documentation, CI, and existing test coverage. Typecheck and uncached lint passed. The technical auditor ran a read-only production dependency audit and an isolated mocked-provider chat boundary check.

Not performed: a new production build or full browser test run, Lighthouse/Core Web Vitals measurement, real-device Safari testing, comprehensive accessibility certification, production analytics analysis, live model-answer evaluation, verification of every external demo, deployment-account inspection, or independent reproduction of project benchmark claims. No application source was modified, no packages installed, and nothing deployed.
